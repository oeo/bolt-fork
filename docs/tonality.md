# tonality

bolt documentation uses direct, factual language.

## rules

- write prose and headings in lowercase.
- preserve exact casing for code identifiers, commands, paths, protocols, and quoted output.
- use short declarative sentences.
- omit hype, emoji, exclamation marks, and marketing claims.
- state limitations and failure modes directly.
- distinguish implemented, tested, and planned behavior.
- do not present planned behavior as available.
- do not publish volatile counts or performance claims without generated evidence.
- name evidence source and measurement conditions when reporting numbers.

## examples

- use: `peer discovery is planned.`
- use: `invalid signatures are rejected and covered by unit tests.`
- use: `BlockHeader` preserves identifier casing.
- avoid: `bolt delivers unmatched performance.`
- avoid: `all tests pass.` without current generated output.
